Chosen design (user picked: interactive bot opponent + autonomous bot I tune, no live command channel):
- **Synthetic-input substrate**: bot players carry a bare `ActionState<Action>` and NO `InputMap`; a driver writes intent `.before(handle_characters_input)` so the bot goes through the *same* gated shoot/charge path a human does. Do NOT shortcut via raw `EntityMoved`/`BeamFired` (bypasses gates; `spend_charge_on_fire` would fire free beams at 0 charges).
- **Stage 0 spike first**: verify `just_pressed(Shoot)` actually fires on a manually-driven bare `ActionState` (leafwing 0.20 may only tick states that have an `InputMap`). Fallback: tick it ourselves, or emit `BeamFired` for Shoot only after replicating the `has_charges`+`resolve_fire` gate.
- **Bot**: `src/plugins/bot.rs`. Policy **v2** (after first playtest showed v1 oscillated at territory borders + felt too fast): beat-paced deliberation (`think_interval_ms`, default 150), Dijkstra pathfinding where entering an enemy tile costs `hostile_cost` (default 20; the stay-safe↔push-through / "prefer safe route" knob — replaces the old reflexive-retreat oscillation), and decoupled aiming — stands on an unclaimed tile and sweep-fires the best-`reach` cardinal, committing to current facing until exhausted then rotating (fixes tied-reach swivel). Knobs: `fire_cooldown_ms` 400, `aggression` 0.5, `think_interval_ms` 150, `hostile_cost` 20 — all `[live]`. Key mechanic: a Straight beam claims only the FARTHEST unclaimed tile in a line and the firing tile stays unclaimed, so sweep-firing from one vantage claims many tiles. **Beam self-claim rule (important, verified in `beam.rs:213-233`):** on the first step a straight beam sits on its ORIGIN; if the next tile is blocked (claimed or off-map) it resolves on the origin — i.e. **firing from an unclaimed tile into a blocked neighbour claims the tile you're standing on.** So EVERY shot from an unclaimed tile claims exactly one tile (far tile down a runway, else the origin itself); "hole" tiles ARE claimable by standing on them and firing any direction. (Earlier I wrongly assumed holes were unclaimable — corrected.) **Ping-pong fix (from a playtest trace):** the bug was a `reach>=1` gate that made the bot refuse to fire with no runway, so it never self-claimed and looped between two holes forever. Fix: fire to self-claim the current tile when no runway (`best_fire` None → fire current facing); target ANY reachable unclaimed tile; opponent-pressure fallback only when board fully claimed. Which `player_id`s are bots: `controllers.player{1,2}_bot` in `game_config.ron`.
- **Play telemetry (user-requested: human + bot), built early**: gitignored JSONL (`play_trace.jsonl`, module `src/plugins/telemetry.rs`), **rolling reset per session** — rotate keep-last-N (`play_trace.jsonl`→`.1`→`.2`, N configurable, default 3) at startup so recent tuning runs stay on disk for comparison; self-describing header line (config + loadouts) first. Every record tagged `controller:"human"|"bot"` — one tagged file, NOT two (keeps within-round correlation trivial). Human records = actions+state only (no self-reported reason; optional `inferred:true` behaviour tag); bot records add the computed `why`. Human play is the ground-truth balance signal + bot imitation target. Sink + per-round outcome summaries + human-action records are bot-independent → **Stage 1** (validate on human-vs-human). Bot decision records need the bot → wired in at bot stage. Stage order: 0 spike → 1 telemetry(sink+outcomes+human) → 2 substrate → 3 bot+bot-decision-records → 4 tuning loop.
- **Out of scope for now**: headless batch-stats harness (needs FixedUpdate + windowless asset-load refactor; low value with only 1 of 34 abilities implemented), scripted timeline, live command channel.
